Model · View · ViewModel

A way to organize your SwiftUI app so that data, screen, and the brains in between each live in their own place. Once you see it, you'll never want to stuff everything into ContentView again.

01 · The problem

Why not just put everything in ContentView?

You can — and for a 20-line demo it's fine. But real apps grow. Soon one file holds the data, the rules, the networking, and the layout. That file becomes impossible to test, hard to reuse, and scary to change.

😵 The "Massive View" problem

A 600-line ContentView where a button tap, a sort function, and a VStack are all tangled together. Change one color, break the sorting.

🧪 Hard to test

You can't easily unit-test "does adding a task work?" when the logic lives inside a view that only exists while it's on screen.

♻️ No reuse

Want the same task logic on an iPad layout or a widget? If it's welded to one View, you copy-paste and now maintain two copies.

MVVM's promise: each piece has one job. The Model holds data. The View draws. The ViewModel connects them and holds the logic. Change one without fear of breaking the others.
02 · Definitions you'll actually remember

Three layers, three jobs

🥕

Model DATA

The raw facts of your app — the what.

  • Plain Swift structs (sometimes enums)
  • Knows nothing about SwiftUI — no import SwiftUI
  • Example: TodoItem with a title and isDone
  • Metaphor: the ingredients in the kitchen. A carrot doesn't know what plate it ends up on.
🍽️

View SCREEN

What the user sees and touches — the look.

  • SwiftUI struct ... : View with a body
  • Should be dumb: it displays and forwards taps, it doesn't decide
  • Example: TaskListView with a List and a Button
  • Metaphor: the plate and the dining room. Beautiful presentation, no cooking.
👨‍🍳

ViewModel LOGIC

The brain between them — the how.

  • A class marked @Observable
  • Owns the Model, exposes ready-to-display values, and has the functions the View calls
  • Example: TaskListViewModel with addTask() and remainingText
  • Metaphor: the chef. Takes orders from the dining room, works with the ingredients, sends back finished plates.

🍴 The restaurant, start to finish

  1. A customer (the user) taps "Add task" in the dining room (View).
  2. The waiter carries the order to the kitchen — that's the View calling viewModel.addTask().
  3. The chef (ViewModel) grabs ingredients (Model) and prepares the dish — appends a new TodoItem to the array.
  4. Because the ViewModel is @Observable, SwiftUI automatically notices the change and re-plates the dining room. You never write "refresh the screen."

Think of a smart TV:

  • Model = the broadcast signal / the movie file. Pure content.
  • View = the screen and the remote buttons. You see pixels, you press things.
  • ViewModel = the TV's processor. It receives "volume up," changes the volume value, and tells the screen to show the new volume bar.

The remote never edits the movie file directly — it always goes through the processor.

Not sure where something belongs? Ask:

"Would this still make sense if my app had no screen at all?" → Model.

"Is this only about how things look or where they're placed?" → View.

"Is this a decision, a calculation, or a response to a user action?" → ViewModel.

🧪 Why the protocol?
In a test you write GradesViewModel(service: FakeService()) that returns instantly, then assert gpaText == "GPA 3.47". No network, no Xcode simulator, runs in milliseconds.

      
🚦 Why an enum for state?
Three Bools (isLoading, hasError, isEmpty) can be true at the same time by accident. An enum makes impossible states impossible — the screen is in exactly one state.

      
🧵 Why @MainActor?
Data arrives on a background thread; UI updates must happen on the main thread. Marking the ViewModel @MainActor guarantees every property change is safe for SwiftUI.

import Foundation
import Observation

@Observable
class TaskListViewModel {
    var tasks: [TodoItem] = [
        TodoItem(title: "Read Chapter 5"),
        TodoItem(title: "Finish Lab 3")
    ]
    var newTitle: String = ""

    var remainingText: String {
        let left = tasks.filter { !$0.isDone }.count
        return "\(left) task\(left == 1 ? "" : "s") left"
    }
    // addTask(), toggle(_:), delete(at:) …
}

    07 · Before you submit
    
Common mistakes (and how to spot them)

    

      
❌ import SwiftUI in the Model
If your struct needs Color or Image, it has become a View concern. Store a plain value (e.g. priority: Int) and let the View map it to a color.

      
❌ Logic inside Button { }
Button { if !title.isEmpty { tasks.append(...) ; title = "" } } → move all of that into viewModel.addTask(). The button body should be one call.

      
❌ Forgetting @Observable
Your ViewModel changes but the screen doesn't update. The class must be marked @Observable and the View must hold it with @State.

      
❌ Making the ViewModel a struct
Structs are copied; SwiftUI can't watch a copy. ViewModels are classes. Models are usually structs.

      
❌ Formatting in the View
Text("\(count) task\(count == 1 ? "" : "s")") in the View is logic. Expose remainingText from the ViewModel and the View just shows it.

      
❌ The View reaching past the ViewModel
If a View ever does viewModel.model.something = ..., the chef is being bypassed. Add a method on the ViewModel instead.
