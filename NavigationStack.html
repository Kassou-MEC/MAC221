Why Do Apps Need Navigation?

Easy

Almost every iOS app has more than one screen: Settings → Wi-Fi → a network; Mail → Inbox → a message. Moving between screens, and being able to go back, is navigation.

Navigation is the mechanism that lets a user move from one view (screen) to another while the app remembers where they came from, so they can return.

Think of a stack of index cards. Opening a screen places a card on top; tapping Back removes the top card and reveals the one underneath.

Home (root)
→
Detail
→
More Detail
⟵ Back pops the top card
NavigationStack is the SwiftUI container (iOS 16+) that manages this stack of views. It draws the navigation bar, adds the Back button automatically, and remembers the path the user has taken.
Heads up
Before iOS 16, SwiftUI used NavigationView. It still compiles but is deprecated. In this course we only use NavigationStack.

Your First NavigationStack

Easy

Each example in this lecture is one file: ContentView.swift. Replace the file Xcode generates with the code shown, and the #Preview at the bottom will run on the canvas.

NavigationLink is a tappable view that, when pressed, pushes a destination view onto the NavigationStack.

EXAMPLE 2.1 One link, one text destination

ContentView.swifthover a line
import SwiftUI

struct ContentView: View {
    var body: some View {
        NavigationStack {
            NavigationLink("Go to Detail Screen") {
                Text("🎉 You navigated!")
                    .font(.title)
            }
            .navigationTitle("Home")
        }
    }
}

}
▶
Preview: a screen titled “Home” with a blue link. Tap it and “🎉 You navigated!” slides in with an automatic < Home back button.
Key idea
The Back button is free. You never write code for it — NavigationStack adds it to every pushed screen.

EXAMPLE 2.2 Destination as its own struct (same file)

A destination that is more than a line of text should be its own struct. It can live in the same file — a Swift file may contain as many structs as you like.

ContentView.swifthover a line
import SwiftUI

// MARK: - Root screen
struct ContentView: View {
    var body: some View {
        NavigationStack {
            VStack(spacing: 20) {
                Text("Welcome to MAC221").font(.largeTitle)
                NavigationLink("Open Detail") {
                    DetailView()
                }
            }
            .navigationTitle("Home")
        }
    }
}

// MARK: - Detail screen
struct DetailView: View {
    var body: some View {
        VStack(spacing: 12) {
            Image(systemName: "star.fill")
                .font(.system(size: 80))
                .foregroundStyle(.yellow)
            Text("This is the detail screen")
        }
        .navigationTitle("Detail")
    }
}

#Preview("Root") {
    ContentView()
}

#Preview("Detail only") {
    NavigationStack { DetailView() }
}
▶
Preview: two previews appear in the canvas tabs — “Root” and “Detail only”. The second shows the star screen with its “Detail” title.
Common mistake
Only one NavigationStack per flow, at the root. A second one inside DetailView gives you two navigation bars and broken Back behavior.

Many Screens, Still One File

Easy

Let's grow to three screens: Home → Profile, Home → Settings, and a nested push Profile → Edit. One file, four structs.

EXAMPLE 3.1 Multiple links and a nested push

ContentView.swifthover a line
import SwiftUI

struct ContentView: View {
    var body: some View {
        NavigationStack {
            List {
                NavigationLink("👤 Profile") { ProfileView() }
                NavigationLink("⚙️ Settings") { SettingsView() }
            }
            .navigationTitle("Home")
        }
    }
}

struct ProfileView: View {
    var body: some View {
        VStack(spacing: 16) {
            Image(systemName: "person.circle.fill").font(.system(size: 90))
            Text("Khalid K.").font(.title)
            NavigationLink("Edit Profile") { EditProfileView() }
        }
        .navigationTitle("Profile")
    }
}

struct EditProfileView: View {
    @State private var name = "Khalid K."
    var body: some View {
        Form {
            TextField("Name", text: $name)
        }
        .navigationTitle("Edit")
    }
}

struct SettingsView: View {
    @State private var darkMode = false
    var body: some View {
        Form {
            Toggle("Dark Mode", isOn: $darkMode)
        }
        .navigationTitle("Settings")
    }
}

#Preview {
    ContentView()
}
▶
Preview: a “Home” list with two rows and chevrons. Profile → Edit Profile pushes a third screen; the back button on Edit reads < Profile, not Home.
Notice
The Back button’s label is always the title of the previous screen. That is why giving every screen a .navigationTitle matters.

Passing Data to the Next Screen

Medium

A detail screen usually shows information about something the user picked. The simplest way: give the destination struct a property, and pass a value when you create it.

EXAMPLE 4.1 One detail struct, reused with different data

ContentView.swifthover a line
import SwiftUI

struct ContentView: View {
    var body: some View {
        NavigationStack {
            List {
                NavigationLink("MAC221 – SwiftUI") {
                    CourseDetailView(courseName: "MAC221", credits: 3)
                }
                NavigationLink("MAC286 – Data Structures") {
                    CourseDetailView(courseName: "MAC286", credits: 4)
                }
                NavigationLink("MAC280 – Unity") {
                    CourseDetailView(courseName: "MAC280", credits: 3)
                }
            }
            .navigationTitle("Courses")
        }
    }
}

struct CourseDetailView: View {
    let courseName: String
    let credits: Int

    var body: some View {
        VStack(spacing: 12) {
            Text("Course: \(courseName)").font(.title)
            Text("Credits: \(credits)")
        }
        .navigationTitle(courseName)
    }
}

#Preview("List") {
    ContentView()
}

#Preview("Detail") {
    NavigationStack {
        CourseDetailView(courseName: "MAC221", credits: 3)
    }
}
▶
Preview: “Courses” list with three rows. Each row opens the same layout with its own name, credits and bar title.
Why this matters
One screen struct, infinite variations. Views are functions of their data.
Problem ahead
Writing a NavigationLink by hand for each course doesn’t scale. What if 50 courses come from a database? Section 5 fixes that.
5

Lists + Value-Based Navigation

Medium

The modern, scalable pattern: instead of telling each link which view to show, we tell it which value was selected, and describe once how to turn any value into a screen.

NavigationLink(value:) pushes a value (a struct, an Int…) instead of a view.

.navigationDestination(for:) registers a rule: “whenever a value of this type is pushed, build this view for it.”
Hashable is a Swift protocol that lets a type be compared and used as a lookup key. NavigationStack requires every pushed value to be Hashable so it can track it. Simple structs get Hashable for free just by declaring it.

EXAMPLE 5.1 A model, a list, one destination rule

ContentView.swifthover a line
import SwiftUI

// MARK: - Model
struct Course: Identifiable, Hashable {
    let id = UUID()
    let code: String
    let title: String
    let credits: Int
}

let sampleCourses = [
    Course(code: "MAC221", title: "iOS App Development", credits: 3),
    Course(code: "MAC280", title: "Game Programming", credits: 3),
    Course(code: "MAC286", title: "Data Structures", credits: 4)
]

// MARK: - Screens
struct ContentView: View {
    var body: some View {
        NavigationStack {
            List(sampleCourses) { course in
                NavigationLink(value: course) {
                    VStack(alignment: .leading) {
                        Text(course.code).font(.headline)
                        Text(course.title).foregroundStyle(.secondary)
                    }
                }
            }
            .navigationTitle("MEC Courses")
            .navigationDestination(for: Course.self) { course in
                CourseDetailView(course: course)
            }
        }
    }
}

struct CourseDetailView: View {
    let course: Course
    var body: some View {
        VStack(spacing: 12) {
            Text(course.title).font(.title)
            Text("\(course.credits) credits").foregroundStyle(.secondary)
        }
        .navigationTitle(course.code)
    }
}

#Preview {
    ContentView()
}
▶
Preview: a “MEC Courses” list of three two-line rows. Tapping any row pushes its detail — and adding a 4th course to sampleCourses needs zero new navigation code.
Two halves of one idea
NavigationLink(value:) = “what was tapped”. .navigationDestination(for:) = “how to show it”. They must agree on the type (here, Course).
Where to attach navigationDestination
Attach it to a view inside the NavigationStack (the List is perfect). Do not attach it to the NavigationLink itself — it won’t work inside lazy containers like List.

Programmatic Navigation with NavigationPath

Harder

So far the user drives navigation by tapping. Often the code must navigate: after login succeeds, when a timer fires, or when a “Finish” button should jump all the way back to the start.

NavigationPath is a type-erased collection representing the current stack of pushed values. Bind it to the NavigationStack and you can read and modify the stack from code: append to push, removeLast to pop.
Programmatic navigation means changing screens by changing state, not by tapping a link. The stack is just data — change the data, and the UI follows.

EXAMPLE 6.1 A 3-question quiz flow with pop-to-root

ContentView.swifthover a line
import SwiftUI

struct ContentView: View {
    @State private var path = NavigationPath()

    var body: some View {
        NavigationStack(path: $path) {
            VStack(spacing: 20) {
                Text("MAC221 Quiz").font(.largeTitle)
                Button("Start Quiz") {
                    path.append(1)
                }
                .buttonStyle(.borderedProminent)
            }
            .navigationTitle("Quiz")
            .navigationDestination(for: Int.self) { number in
                QuestionView(number: number, path: $path)
            }
        }
    }
}

struct QuestionView: View {
    let number: Int
    @Binding var path: NavigationPath

    var body: some View {
        VStack(spacing: 20) {
            Text("Question \(number) of 3").font(.title)
            if number < 3 {
                Button("Next") { path.append(number + 1) }
            } else {
                Button("Finish 🎓") { path.removeLast(path.count) }
            }
        }
        .navigationTitle("Q\(number)")
    }
}

#Preview {
    ContentView()
}
▶
Preview: “Quiz” with a Start button. Start → Q1 → Q2 → Q3 → Finish pops straight back to “Quiz” in one animation.
ActionCodePath becomes
Push question 1path.append(1)[1]
Push question 2path.append(2)[1, 2]
Go back onepath.removeLast()[1]
Pop to rootpath.removeLast(path.count)[ ] (empty)
Mental model
The stack of screens is a mirror of the path. You never “navigate” — you edit an array, and SwiftUI navigates for you.

Mixing Screen Types with a Route Enum

Advanced

Real apps push many kinds of screens: a course, a student, settings. The professional pattern is an enum that lists every screen the app can push, with associated values carrying the data each screen needs.

Route enum: a Hashable enum where each case is one kind of screen. Using [Route] as the path makes navigation type-safe — the compiler forces you to handle every screen.

EXAMPLE 7.1 Dashboard with three screen types and a deep link

ContentView.swifthover a line
import SwiftUI

// MARK: - Models
struct Course: Identifiable, Hashable {
    let id = UUID()
    let code: String
    let credits: Int
}

struct Student: Hashable {
    let name: String
    let major: String
}

// MARK: - Routes
enum Route: Hashable {
    case course(Course)
    case student(Student)
    case settings
}

let sampleCourses = [
    Course(code: "MAC221", credits: 3),
    Course(code: "MAC286", credits: 4)
]

// MARK: - Screens
struct ContentView: View {
    @State private var path: [Route] = []
    let student = Student(name: "Amina", major: "Computer Science")

    var body: some View {
        NavigationStack(path: $path) {
            List {
                Section("Courses") {
                    ForEach(sampleCourses) { course in
                        NavigationLink(course.code, value: Route.course(course))
                    }
                }
                Section("People") {
                    NavigationLink(student.name, value: Route.student(student))
                }
                Section("Actions") {
                    Button("Open Settings") { path.append(.settings) }
                    Button("Jump: Course → Student") {
                        path.append(.course(sampleCourses[0]))
                        path.append(.student(student))
                    }
                }
            }
            .navigationTitle("Dashboard")
            .navigationDestination(for: Route.self) { route in
                switch route {
                case .course(let c):   CourseScreen(course: c)
                case .student(let s):  StudentScreen(student: s)
                case .settings:        SettingsScreen()
                }
            }
        }
    }
}

struct CourseScreen: View {
    let course: Course
    var body: some View {
        Text("\(course.code) – \(course.credits) credits")
            .navigationTitle(course.code)
    }
}

struct StudentScreen: View {
    let student: Student
    var body: some View {
        Text("\(student.name) – \(student.major)")
            .navigationTitle(student.name)
    }
}

struct SettingsScreen: View {
    var body: some View {
        Text("Settings").navigationTitle("Settings")
    }
}

#Preview {
    ContentView()
}
▶
Preview: a grouped “Dashboard” list. Tap “Jump: Course → Student” and you land on Amina’s screen; Back reveals MAC221 underneath, then Dashboard.
NavigationPath vs. [Route]
NavigationPath: flexible, holds any Hashable, but you can’t easily read what’s inside. [Route]: strict and self-documenting; the compiler enforces every screen. Prefer it for real apps.

Polish: Toolbar, Dismiss & Display Mode

Harder

A few modifiers that make navigation feel professional. Students ask about these constantly.

EXAMPLE 8.1 Toolbar button, custom Done, inline title

ContentView.swifthover a line
import SwiftUI

struct ContentView: View {
    var body: some View {
        NavigationStack {
            NavigationLink("Open polished screen") { PolishedView() }
                .navigationTitle("Home")
        }
    }
}

struct PolishedView: View {
    @Environment(\.dismiss) private var dismiss
    @State private var isFavorite = false

    var body: some View {
        VStack(spacing: 16) {
            Text("Polished Screen").font(.title)
            Button("Done") { dismiss() }
                .buttonStyle(.bordered)
        }
        .navigationTitle("Details")
        .navigationBarTitleDisplayMode(.inline)
        .navigationBarBackButtonHidden(true)
        .toolbar {
            ToolbarItem(placement: .topBarTrailing) {
                Button {
                    isFavorite.toggle()
                } label: {
                    Image(systemName: isFavorite ? "heart.fill" : "heart")
                }
            }
        }
    }
}

#Preview("Home") {
    ContentView()
}

#Preview("Polished") {
    NavigationStack { PolishedView() }
}
▶
Preview: the “Polished” preview shows a small centered title, a heart in the top-right that toggles, no Back button, and a Done button that pops the screen.
Styling the whole bar
Use .toolbarBackground(.visible, for: .navigationBar) and .toolbarColorScheme(.dark, for: .navigationBar) on the root content to style the bar app-wide.
