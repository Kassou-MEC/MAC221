How a Real Project Is Organized

Easy

In Part 1, one file held the model, every screen, and the preview. That is fine for learning, but a real app with 20 screens in one file is painful. Professionals split code by responsibility.

Separation of concerns: each file does one job. Models describe data. Views draw screens. Navigation code decides how screens connect. When something breaks, you know which file to open.
MECApp/ ├── MECApp.swift // @main — the app entry point ├── Models/ │ └── Course.swift // data only ├── Navigation/ │ ├── Route.swift // every screen the app can push │ └── Router.swift // shared navigation state └── Views/ ├── ContentView.swift ├── CourseListView.swift └── CourseDetailView.swift

The folders are Xcode groups: right-click the project → New Group. They don’t change how Swift compiles anything — every file in the target can see every other file, no import needed between them.

The one rule about imports
Every file that uses SwiftUI types (View, Text, NavigationStack…) needs import SwiftUI. A pure data file only needs import Foundation. You never import your own files.
What about the App file?
Xcode creates it for you (named after your project, e.g. MECApp.swift). It contains the @main struct. We will edit it in Section 3 to inject the Router.

A Shared Router with @Observable

Medium

In Part 1 Section 6, we passed $path down as a @Binding. With 10 screens that becomes "binding spaghetti". The fix: put the path in a single Router object that any screen can reach through the environment.

@Observable (iOS 17) marks a class so SwiftUI automatically re-renders any view that reads one of its properties when that property changes.
Environment injection: .environment(object) places an object into the view tree; any descendant reads it with @Environment(Type.self). No manual passing through every initializer.

EXAMPLE 3.1 Route + Router + injection in the App file

MECApp/ ├── MECApp.swiftEDIT ├── Models/ └── Course.swift // unchanged ├── Navigation/ ├── Route.swiftNEW └── Router.swiftNEW └── Views/ ├── ContentView.swiftEDIT ├── CourseDetailView.swiftEDIT └── SettingsView.swiftNEW

Navigation/Route.swift

Route.swifthover a line
import Foundation

enum Route: Hashable {
    case course(Course)
    case settings
}

Navigation/Router.swift

Router.swifthover a line
import SwiftUI

@Observable
final class Router {
    var path: [Route] = []

    func push(_ route: Route) {
        path.append(route)
    }

    func pop() {
        if !path.isEmpty { path.removeLast() }
    }

    func popToRoot() {
        path = []
    }
}

MECApp.swift

MECApp.swifthover a line
import SwiftUI

@main
struct MECApp: App {
    @State private var router = Router()

    var body: some Scene {
        WindowGroup {
            ContentView()
                .environment(router)
        }
    }
}

Views/ContentView.swift

ContentView.swifthover a line
import SwiftUI

struct ContentView: View {
    @Environment(Router.self) private var router

    var body: some View {
        @Bindable var router = router

        NavigationStack(path: $router.path) {
            List {
                Section("Courses") {
                    ForEach(Course.samples) { course in
                        NavigationLink(course.code, value: Route.course(course))
                    }
                }
                Section {
                    Button("Settings") { router.push(.settings) }
                }
            }
            .navigationTitle("MEC")
            .navigationDestination(for: Route.self) { route in
                switch route {
                case .course(let c): CourseDetailView(course: c)
                case .settings:      SettingsView()
                }
            }
        }
    }
}

TabView: One Stack Per Tab

Medium

Most apps have a tab bar. The rule is simple and important: each tab owns its own NavigationStack. Pushing inside the Courses tab must not affect the Profile tab.

TabView shows a bottom tab bar and switches between its child views. Each child is typically a NavigationStack, so each tab keeps an independent navigation history.

Sheets vs. Push: Choosing a Presentation

Medium

Not every new screen belongs on the stack. iOS has two main ways to show something: push (slide in from the right, part of a flow) and modal (slide up from the bottom, a temporary task).

Sheet: a modal card that slides up and can be swiped down. Use it for a short, self-contained task — add an item, compose, pick an option. .sheet(isPresented:) or .sheet(item:).
Full-screen cover: a modal that covers everything and cannot be swiped away. Use it for onboarding, login, or a video player. .fullScreenCover(…).
SituationUseWhy
Course list → course detailPushDrilling deeper into the same content
“Add Course” formSheetTemporary task; cancel returns to where you were
Login screen before anything elseFull-screen coverMust not be dismissed by a swipe
SettingsEitherApple pushes; many apps present a sheet

import SwiftUI

struct AddCourseView: View {
    @Environment(\.dismiss) private var dismiss
    let onSave: (Course) -> Void
    @State private var code = ""
    @State private var title = ""

    var body: some View {
        NavigationStack {
            Form {
                TextField("Code (e.g. MAC283)", text: $code)
                TextField("Title", text: $title)
            }
            .navigationTitle("New Course")
            .navigationBarTitleDisplayMode(.inline)
            .toolbar {
                ToolbarItem(placement: .cancellationAction) {
                    Button("Cancel") { dismiss() }
                }
                ToolbarItem(placement: .confirmationAction) {
                    Button("Save") {
                        onSave(Course(code: code, title: title, credits: 3))
                        dismiss()
                    }
                    .disabled(code.isEmpty || title.isEmpty)
                }
            }
        }
    }
}

Push vs. sheet, in one line
Push = “go deeper”. Sheet = “do something, then come back”. If you would be annoyed to see it in the Back history, it should be a sheet.
.sheet(item:) variant
When the sheet needs data, use @State private var editing: Course? and .sheet(item: $editing) { course in … }. Setting editing = someCourse presents; SwiftUI sets it back to nil on dismiss.

Deep Links: Opening a Screen From a URL

Harder

Tap a link in Messages, a notification, or a QR code and the app opens directly on the right screen. With a Router that is only a few lines.

Deep link: a URL like mecapp://course/MAC221 that the system hands to your app. Your code parses it and builds the matching navigation path.
URL scheme: the part before ://. You register it once in Xcode so iOS knows which app owns it.
Xcode setup (one time)
Project → target → Info tab → URL Types → + → Identifier edu.lagcc.mec, URL Schemes mecapp. That's it.

EXAMPLE 6.1 Parse a URL into a Route

MECApp/ ├── Navigation/ ├── Router.swiftEDIT └── DeepLinkParser.swiftNEW └── Views/ └── CoursesTab.swiftEDIT

Navigation/DeepLinkParser.swift

DeepLinkParser.swifthover a line
import Foundation

enum DeepLinkParser {
    static func routes(from url: URL) -> [Route]? {
        guard url.scheme == "mecapp" else { return nil }

        switch url.host {
        case "course":
            guard let code = url.pathComponents.last,
                  let course = Course.samples.first(where: { $0.code == code })
            else { return nil }
            return [.course(course)]
        case "settings":
            return [.settings]
        default:
            return nil
        }
    }
}

Navigation/Router.swift

Router.swifthover a line
import SwiftUI

@Observable
final class Router {
    var path: [Route] = []

    func push(_ route: Route) { path.append(route) }
    func pop() { if !path.isEmpty { path.removeLast() } }
    func popToRoot() { path = [] }

    func handle(_ url: URL) {
        guard let routes = DeepLinkParser.routes(from: url) else { return }
        path = routes
    }
}

Test it: run on the simulator, then in Terminal: xcrun simctl openurl booted "mecapp://course/MAC286". The app opens straight onto MAC286 with a Back button to Courses. Try mecapp://settings too.
Multi-screen deep links
Because the parser returns [Route], mecapp://course/MAC221/related could return [.course(a), .course(b)] and the user would land two levels deep with a sensible Back trail.
Which tab receives the URL?
.onOpenURL fires on every view that declares it. In a tabbed app, handle it once at the TabView level, select the right tab, then route — or keep it on the one tab that owns those routes, as here.
7

Saving & Restoring the Navigation Path

Advanced

Open a course, go back to the home screen, and iOS may quit your app in the background. When the user returns, a polished app is still on that course. To do that, we save the path when it changes and restore it on launch.

Codable: a Swift protocol that lets a type be converted to and from Data (usually JSON). If every piece of a Route is Codable, the whole [Route] array is Codable for free.
@SceneStorage: a property wrapper that persists a small value per window/scene across app restarts. Perfect for navigation state; not for user data.

EXAMPLE 7.1 Make Route Codable, persist with @SceneStorage

MECApp/ ├── Models/ └── Course.swiftEDIT ├── Navigation/ └── Route.swiftEDIT └── Views/ └── CoursesTab.swiftEDIT

Models/Course.swift

import Foundation

struct Course: Identifiable, Hashable, Codable {
    var id = UUID()
    let code: String
    let title: String
    let credits: Int

    static let samples = [
        Course(code: "MAC221", title: "iOS App Development", credits: 3),
        Course(code: "MAC280", title: "Game Programming", credits: 3),
        Course(code: "MAC286", title: "Data Structures", credits: 4)
    ]
}

Navigation/Route.swift

Route.swifthover a line
import Foundation

enum Route: Hashable, Codable {
    case course(Course)
    case settings
}

Views/CoursesTab.swift

CoursesTab.swifthover a line
import SwiftUI

struct CoursesTab: View {
    @State private var router = Router()
    @State private var courses = Course.samples
    @State private var showingAdd = false
    @SceneStorage("coursesPath") private var savedPath: Data?

    var body: some View {
        NavigationStack(path: $router.path) {
            List(courses) { course in
                NavigationLink(course.code, value: Route.course(course))
            }
            .navigationTitle("Courses")
            .toolbar {
                Button("Add", systemImage: "plus") { showingAdd = true }
            }
            .navigationDestination(for: Route.self) { route in
                switch route {
                case .course(let c): CourseDetailView(course: c)
                case .settings:      SettingsView()
                }
            }
            .sheet(isPresented: $showingAdd) {
                AddCourseView { courses.append($0) }
            }
        }
        .environment(router)
        .onOpenURL { router.handle($0) }
        .onChange(of: router.path) {
            savedPath = try? JSONEncoder().encode(router.path)
        }
        .task {
            if let data = savedPath,
               let routes = try? JSONDecoder().decode([Route].self, from: data) {
                router.path = routes
            }
        }
    }
}

#Preview {
    CoursesTab()
}
▶
Test it: run on the simulator, open MAC280, then Stop in Xcode and Run again. The app launches directly on MAC280, Back button intact.
Why this cannot use plain NavigationPath
NavigationPath hides its contents (type-erased). It does offer path.codable, but only when every value inside is Codable, and the API is clumsier. A typed [Route] array is simply Codable — one more reason to prefer it.
@SceneStorage vs @AppStorage
@SceneStorage is per window and restored by the system only for state restoration — exactly what navigation wants. @AppStorage is UserDefaults: global, permanent, better for settings.
