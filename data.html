// 03 · the problem

Your apps have amnesia

Try this with any app you've built so far: open it, do some work, then force-quit and reopen. Everything is gone. Your beautiful UI just lost its memory.

⚠ Try this with the Mood Tracker:
  1. Open the app, save 5 moods
  2. Swipe up from the bottom to kill the app
  3. Reopen the app
  4. Your history is empty. All data lost.

▸ Why does this happen?

Every variable in your code lives in RAM — the phone's short-term memory. When iOS shuts down your app, RAM is wiped clean. To survive, data must be written to permanent storage: a file on disk, the system's UserDefaults database, or a SwiftData store.

💡 The key insight: @State and @Published only persist as long as the app is alive. They are NOT storage. They are RAM-backed state, which means temporary by design.

▸ Part One
@AppStorage
The simplest possible way to make a value survive app restarts. One property wrapper. One line of code. Done.
// 05 · concept

What is @AppStorage?

A property wrapper that looks like @State, but its value is automatically saved to the system's UserDefaults database. The phone remembers it forever — even after restarting.

⚡

One line of code

Replace @State with @AppStorage("key"). SwiftUI handles save and load automatically.

🔑

Key-based

Each value has a string key like "username". The key is how iOS finds your data later.

⚖️

Limited types

Only basic types: Bool, Int, Double, String, URL, Data. Not arrays or structs.

💡 Easy way to remember: @AppStorage is for the SAME kind of small values you'd find in the iPhone Settings app — toggles, sliders, usernames, color choices. Anything that fits in one row.
⚠ When NOT to use it: If your data is a list, an array of custom objects, or anything bigger than ~1KB — use Part 2 (JSON files) or Part 3 (SwiftData) instead.
// 06 · easiest possible example

Your first @AppStorage

Let's start with the simplest case: a toggle for dark mode. The user flips it once — and the next time they open the app, it remembers their choice.

SimpleAppStorage.swift
● Basic
import SwiftUI

struct SettingsView: View {
    @AppStorage("darkMode") var darkMode = false

    var body: some View {
        Form {
            Toggle("Dark Mode", isOn: $darkMode)
        }
    }
}
▸ What each line does
  1. @AppStorage("darkMode") — the property wrapper. The string "darkMode" is the unique KEY for saving this value.
  2. var darkMode = false — the variable. false is the DEFAULT used the FIRST time the app launches.
  3. Toggle("Dark Mode", isOn: $darkMode) — the UI. The $ creates a two-way binding (same as @State).
  4. Every time the user flips the toggle, SwiftUI saves the new value to UserDefaults automatically — you do nothing.
  5. Next time the app opens, darkMode starts with whatever the user last chose.
💡 That's it. No save button. No "did the user change it?" check. The phone remembers — forever.

// 07 · using the saved value

Saving is half the job

A saved value is useless if you don't USE it. Here's how to apply the saved darkMode to actually change the app's appearance.

ApplyDarkMode.swift
● Basic
struct SettingsView: View {
    @AppStorage("darkMode") var darkMode = false
    @AppStorage("username") var username = ""
    @AppStorage("fontSize") var fontSize: Double = 16

    var body: some View {
        Form {
            TextField("Your name", text: $username)
            Toggle("Dark Mode", isOn: $darkMode)
            Slider(value: $fontSize, in: 12...24)
            Text("Hello, \(username)!")
                .font(.system(size: fontSize))
        }
        .preferredColorScheme(darkMode ? .dark : .light)
    }
}
▸ Three @AppStorage values working together
  1. Three saved values: a Bool, a String, and a Double. Each has its own unique key.
  2. .preferredColorScheme(darkMode ? .dark : .light) — applies the saved setting to the WHOLE screen.
  3. .font(.system(size: fontSize)) — the text size also reflects the saved slider value.
  4. Change anything, kill the app, reopen — every setting is exactly where the user left it.

// 09 · advanced · enums with @AppStorage

Saving enum choices

You can save an enum if it has a rawValue of String or Int. This is perfect for things like theme selection, language, or user role.

AppStorageEnum.swift
● Intermediate
enum AppTheme: String, CaseIterable {
    case light  = "Light"
    case dark   = "Dark"
    case system = "System"
}

struct ThemeSettings: View {
    @AppStorage("theme") var theme: AppTheme = .system

    var body: some View {
        Picker("Theme", selection: $theme) {
            ForEach(AppTheme.allCases, id: \.self) { t in
                Text(t.rawValue).tag(t)
            }
        }
        .pickerStyle(.segmented)
    }
}
▸ Why this works
  1. enum AppTheme: String — the enum has String raw values. That's the key requirement.
  2. @AppStorage("theme") var theme: AppTheme = .system — saves the rawValue ("System") as a string in UserDefaults.
  3. SwiftUI handles converting between the enum and the string for you. No manual encoding needed.
  4. You get all the benefits of enums (type safety, autocomplete) AND persistence — no compromise.
String-backed enum CaseIterable for ForEach Auto-saved on change

JSON Files
When @AppStorage isn't enough — save arrays of custom structs to a JSON file on disk. The workhorse pattern for medium-sized data.
// 11 · concept

Why JSON files?

@AppStorage hit a wall: it can't save arrays of custom structs. For a list of saved moods, tasks, or contacts, we need a real file on disk. JSON is the universal format for that.

📄

Plain text format

JSON is human-readable. You can open the saved file and inspect it. Great for debugging.

🧬

Codable does the work

Swift converts your structs to JSON and back automatically. You just write : Codable.

💾

Saved on the phone

The file lives in your app's private "Documents" folder. Other apps can't read it. Survives restarts and updates.

💡 Three steps for any JSON-based persistence:
  1. Make your struct Codable (one word)
  2. Use JSONEncoder to convert array → Data, write to disk
  3. Use JSONDecoder to read disk → Data → array on launch
// 12 · prerequisite · Codable

Meet Codable

Codable is a Swift protocol that means "this type can be converted to data and back". One word, and Swift automatically writes the conversion code for you.

CodableStruct.swift
● Basic
struct MoodEntry: Codable, Identifiable {
    let id: UUID
    let mood: String
    let emoji: String
    let intensity: Int
    let timestamp: Date
}

// Now you can convert to/from JSON!
let entry = MoodEntry(id: UUID(), mood: "Great",
                       emoji: "😄", intensity: 9,
                       timestamp: Date())

let jsonData = try! JSONEncoder().encode(entry)
let jsonString = String(data: jsonData, encoding: .utf8)!
// → {"id":"...","mood":"Great","emoji":"😄","intensity":9,...}
▸ What's happening
  1. : Codable — adds two protocols at once: Encodable (object → data) and Decodable (data → object).
  2. You write zero conversion code. Swift inspects your properties and generates the JSON automatically.
  3. JSONEncoder().encode(entry) — converts your struct to Data, which is what files store.
  4. You can convert back the other way with JSONDecoder().decode(MoodEntry.self, from: data).
⚠ The rule: Every property type INSIDE your struct must also be Codable. Strings, Ints, Doubles, Bools, Dates, UUIDs, and arrays of Codable types — all already conform. You almost never have to do anything extra.

▸ What the JSON looks like

{
  "id": "A8F2...",
  "mood": "Great",
  "emoji": "😄",
  "intensity": 9,
  "timestamp": 752183421.5
}

This text gets written to a file. Next launch, we read this text back and Swift rebuilds the struct.

: Codable JSONEncoder() JSONDecoder()

// 14 · file 2 of 3 · the viewmodel

File 2 — MoodViewModel.swift

The brain. Holds the array, exposes addMood / delete functions, and silently handles save/load behind the scenes. The View has no idea persistence exists.

ViewModels/MoodViewModel.swift
● File 2 of 3
import Foundation

class MoodViewModel: ObservableObject {
    @Published var history: [MoodEntry] = []

    // MARK: - File location on disk
    private var fileURL: URL {
        let docs = FileManager.default.urls(for: .documentDirectory, in: .userDomainMask)[0]
        return docs.appendingPathComponent("moods.json")
    }

    // MARK: - Lifecycle
    init() {
        load()   // load existing data when ViewModel is created
    }

    // MARK: - Public actions (the View calls these)
    func addMood(name: String, emoji: String, note: String, intensity: Int) {
        let entry = MoodEntry(mood: name, emoji: emoji, note: note, intensity: intensity)
        history.insert(entry, at: 0)
        save()
    }

    func delete(at offsets: IndexSet) {
        history.remove(atOffsets: offsets)
        save()
    }

    func clearAll() {
        history.removeAll()
        save()
    }

    // MARK: - Private persistence (hidden from the View)
    private func save() {
        guard let data = try? JSONEncoder().encode(history) else { return }
        try? data.write(to: fileURL)
    }

    private func load() {
        guard let data = try? Data(contentsOf: fileURL),
              let decoded = try? JSONDecoder().decode([MoodEntry].self, from: data) else { return }
        history = decoded
    }
}
▸ Read the file top to bottom
  1. @Published var history — the array of moods the View shows. Marked @Published so SwiftUI redraws when it changes.
  2. fileURL — a computed property that builds the path to moods.json in your app's Documents folder. Private, because the View shouldn't know about files.
  3. init() { load() } — runs ONCE when the ViewModel is created. Pulls existing moods off disk before the View renders.
  4. Three public functions: addMood, delete, clearAll — every one calls save() at the end. That's the rule.
  5. private func save() and private func load() — the persistence logic. Marked private so the View can't call them directly. The View shouldn't even know they exist.
💡 The MVVM payoff: The View calls vm.addMood(...) and that's it. It has zero awareness of files, JSON, encoders, or disk. If you ever switch from JSON to SwiftData, you change THIS file only — every View keeps working unchanged. That's the entire point of MVVM.
📂 But wait — who creates the moods.json file?

You don't! iOS handles it. Here's the exact sequence the first time a user runs your app:

  1. App opens for the first time → ViewModel's init() calls load().
  2. load() tries to read moods.json → the file doesn't exist yet.
  3. try? returns nil → guard ... else { return } quietly bails out. No crash. history stays empty [].
  4. User taps "Add Happy" → save() runs → data.write(to: fileURL) creates the file automatically because the Documents/ folder already exists.
  5. App restart → load() now finds the file → user's data comes back.

The takeaway: The file is created on the FIRST save, not on launch. You never have to manually create, open, or close files in Swift.

File 3 — MoodView.swift

Pure UI. Reads from the ViewModel, calls ViewModel functions. Every saved property — mood, emoji, note, intensity, AND timestamp — now appears on screen. Nothing in our Model is wasted.

Views/MoodView.swift
● File 3 of 3
import SwiftUI

struct MoodView: View {
    @StateObject var vm = MoodViewModel()
    @State private var newIntensity: Double = 5

    var body: some View {
        NavigationStack {
            List {
                ForEach(vm.history) { entry in
                    HStack {
                        Text(entry.emoji)
                            .font(.title)
                        VStack(alignment: .leading, spacing: 3) {
                            HStack {
                                Text(entry.mood)
                                    .fontWeight(.semibold)
                                // 👇 intensity badge
                                Text("\(entry.intensity)/10")
                                    .font(.caption)
                                    .foregroundStyle(.white)
                                    .padding(.horizontal, 8)
                                    .padding(.vertical, 2)
                                    .background(.blue)
                                    .clipShape(Capsule())
                            }
                            // 👇 timestamp — auto-updates as "5 min ago"
                            Text(entry.timestamp, style: .relative)
                                .font(.caption2)
                                .foregroundStyle(.tertiary)
                            if !entry.note.isEmpty {
                                Text(entry.note)
                                    .font(.caption)
                                    .foregroundStyle(.secondary)
                            }
                        }
                    }
                }
                .onDelete(perform: vm.delete)
            }
            .navigationTitle("My Moods")
            .safeAreaInset(edge: .bottom) {
                // 👇 intensity slider + Add button pinned to bottom
                VStack(spacing: 8) {
                    Text("Intensity: \(Int(newIntensity))/10")
                        .font(.caption)
                    Slider(value: $newIntensity, in: 1...10, step: 1)
                    Button("Add Happy") {
                        vm.addMood(name: "Happy",
                                    emoji: "😊",
                                    note: "Feeling great today!",

                    }
                    .buttonStyle(.borderedProminent)
                }
                .padding()
                .background(.thinMaterial)
            }

}

▸ What's new — every property now used
  1. @State private var newIntensity: Double = 5 — temporary slider value. Lives in the View, not the ViewModel, because it's UI state before saving.
  2. Text("\(entry.intensity)/10") styled as a blue capsule badge next to the mood name — shows the saved intensity at a glance.
  3. Text(entry.timestamp, style: .relative) — SwiftUI's built-in relative date formatter. Renders as "5 min ago", "Yesterday at 9:41 AM", etc. Auto-updates over time. One line of code.

Where does moods.json live?

A common student question: "I saved data — where IS the file on my computer?" Great instinct. Here are three ways to find it.

▸ Method 1 · Let Swift print the path

Add one line to your ViewModel's init(). Xcode's console will print the exact path every launch.

PrintPath.swift
● Debugging
init() {
    print("📂 File: \(fileURL.path)")
    load()
}

Run the app, look at Xcode's debug console (bottom of the window):

📂 File: /Users/khalid/Library/Developer/
CoreSimulator/Devices/A8F2.../Documents/moods.json

▸ Method 2 · Search with Terminal

No code changes needed. Open Terminal on your Mac and run:

$ find ~/Library/Developer/CoreSimulator \
       -name "moods.json" 2>/dev/null

The 2>/dev/null part hides "permission denied" noise. The command searches every simulator and prints any match it finds.

▸ Method 3 · Open Finder right at the file

Once you have the path, paste it into Terminal with the open command to launch Finder:

$ open "/Users/.../Documents/"
💡 The path is huge — why? The Simulator gives each device and each app a random UUID for isolation. That's why the path has cryptic strings like A8F2-9C1D-.... Real iPhones use the same pattern internally — you just can't browse to it without Xcode.
⚠ The file is missing? Check first. The file is created on the FIRST save, not on app launch. If you haven't tapped "+ Add" yet, moods.json doesn't exist anywhere. Save something first, then look.

▸ The killer demo

🎯 Try this in class:
  1. Run the app. Save one mood.
  2. Find moods.json using Method 2.
  3. Open the file in TextEdit. Change "mood": "Happy" to "mood": "Sad". Save.
  4. Force-quit the app, reopen.
  5. The app shows Sad — your manual edit took effect.

This proves the file is real, the JSON format is universal, and any tool can read or write it. Not just Swift.

🛑 Canvas preview is NOT enough!

If you're only watching the #Preview panel on the right side of Xcode — none of this works. The canvas runs your code in a throwaway process that wipes its disk every time you edit code. No persistent file is created.

You MUST run in the iOS Simulator to test persistence:

  1. Top toolbar → pick a device (e.g. iPhone 15)
  2. Press ⌘+R or click the ▶ button
  3. The Simulator opens with your real app
  4. NOW the file gets created. NOW you can find it.
🔍 Finder's search bar won't find it!

If you type moods.json into Finder's search bar — nothing shows up. That's because the file lives inside the ~/Library folder, which macOS hides from Spotlight indexing by default. The file IS there; the search just can't see it.

The reliable fix — Go to Folder:

  1. Click any Finder window so Finder is the active app
  2. Press ⌘ + ⇧ + G (Cmd + Shift + G)
  3. A small dialog appears with a text field
  4. Paste the full path you got from print(fileURL.path)
  5. Press Enter → Finder jumps right to the folder

Bonus — make Library always visible: Click your home folder in Finder's sidebar, press ⌘+J, scroll down and check "Show Library Folder". From then on, Spotlight indexes it and the search bar works normally.

⚠ ⌘+⇧+. (period) is sometimes recommended to toggle hidden files, but it can be unreliable on some Mac setups. Use Go to Folder instead — it always works.

SwiftData
Apple's modern database. When your data grows up — queries, relationships, undo, iCloud sync — SwiftData is what real iOS apps use.
// 18 · concept

What is SwiftData?

SwiftData is Apple's framework for storing data in a real database. It replaces Core Data for new code, and it's designed to feel like normal Swift — no SQL, no fetch requests, just @Model and @Query.

🗃️

Real database

Backed by SQLite, but you never write SQL. Swift handles it. Fast even with thousands of records.

🔍

Powerful queries

Filter, sort, group with simple Swift syntax. #Predicate lets you say "give me moods from this week, sorted by intensity".

☁️

Auto-sync (optional)

One line of code and your data syncs across iPhone, iPad, and Mac via iCloud. Free.

🔗

Relationships

A User has many Posts. A Post has one Author. SwiftData handles connections between types.

⚠ Requirements: SwiftData requires iOS 17+. For older iOS versions, you need Core Data (much more complex) or stick with JSON files from Part 2.
// 19 · the @Model macro

Defining a @Model

In SwiftData, your data type is a class (not struct) marked with @Model. The macro adds all the database magic behind the scenes — you just write normal Swift properties.

MoodEntry.swift · SwiftData version
● Advanced
import SwiftData
import Foundation

@Model
class MoodEntry {
    var mood: String
    var emoji: String
    var note: String
    var intensity: Int
    var timestamp: Date

    init(mood: String, emoji: String,
         note: String, intensity: Int) {
        self.mood = mood
        self.emoji = emoji
        self.note = note
        self.intensity = intensity
        self.timestamp = Date()
    }
}
▸ The key differences from a normal class
  1. @Model — the macro. Tells Swift "this class is a database record".
  2. class, not struct — SwiftData needs reference types so multiple views can edit the same row.
  3. var properties (not let) — because database records can change after creation.
  4. No Codable needed! SwiftData handles serialization internally.
  5. No id property either — SwiftData generates a unique identifier for every record automatically.

▸ Setting up the container

App.swift
● Setup
@main
struct MoodTrackerApp: App {
    var body: some Scene {
        WindowGroup {
            ContentView()
        }
        .modelContainer(for: MoodEntry.self)
    }
}
💡 One line setup. The .modelContainer(for:) modifier creates the database file, sets up the SwiftData "context", and makes it available to every view. That's it.
// 20 · fetching with @Query

Loading data with @Query

In SwiftData, you don't manually read files. Just declare @Query var moods: [MoodEntry] and SwiftUI automatically gives you the latest data — AND updates the View whenever the database changes.

MoodView.swift · SwiftData
● Advanced
import SwiftUI
import SwiftData

struct MoodView: View {
    @Environment(\.modelContext) var context
    @Query(sort: \MoodEntry.timestamp, order: .reverse)
    var moods: [MoodEntry]

    var body: some View {
        List(moods) { entry in
            HStack {
                Text(entry.emoji).font(.title)
                Text(entry.mood)
            }
        }
    }

    func addMood(name: String, emoji: String) {
        let entry = MoodEntry(mood: name, emoji: emoji,
                              note: "", intensity: 5)
        context.insert(entry)   // 👈 that's the "save"
    }
}
▸ What's happening
  1. @Environment(\.modelContext) — gives the view access to SwiftData's "context", which is how you add/remove data.
  2. @Query(sort:, order:) — automatically fetches all MoodEntry records, sorted by timestamp newest-first.
  3. The view auto-redraws every time the database changes. No @Published, no load() calls, no manual refresh.
  4. context.insert(entry) — adds a new record to the database. SwiftData saves automatically. That's the entire "save" operation.
  5. To delete: context.delete(entry). That's it.

▸ Powerful filtering

FilteredQuery.swift
● Advanced
// Only moods with intensity 7+
@Query(filter: #Predicate<MoodEntry> {
    $0.intensity >= 7
})
var intenseMoods: [MoodEntry]


// Only today's moods, newest first
@Query(
    filter: #Predicate<MoodEntry> {
        $0.timestamp >= Calendar.current
            .startOfDay(for: Date())
    },
    sort: \MoodEntry.timestamp,
    order: .reverse
)
var todaysMoods: [MoodEntry]

This is where SwiftData beats JSON files badly. Imagine doing the same filtering with a JSON array of 5000 moods — you'd have to load all of them into memory first. SwiftData lets the database do the work.

// 21 · reference · which one to use

The decision tree

Take a screenshot of this slide. It's the cheat sheet you'll use the rest of your iOS career to pick the right persistence tool.

Use thisWhenExample
@AppStorage Saving 1 simple value (Bool, Int, String). User-preference territory. Dark mode toggle, font size, "has seen onboarding" flag
JSON file Saving a list of custom structs. Small to medium dataset (under ~10,000 items). Mood history, saved recipes, task list, journal entries
SwiftData Lots of data, complex queries, relationships, iCloud sync, or iOS 17+ targeting. Notes app, fitness tracker, library catalog, real production apps
Server / API Multiple users share the same data. Beyond this lecture. Social feed, multiplayer game, chat app
💡 Senior dev mindset: Pick the SMALLEST tool that solves your problem. Don't reach for SwiftData when @AppStorage will do. Don't reach for JSON files when one Bool will do. Simplicity wins.
⚠ Common beginner mistake: Using @AppStorage to save a "history" array. It won't work — and even if you encode it manually, you'll hit performance issues fast. Use the right tool for the shape of your data.

Five things to remember

If you only retain five points from today's lecture, make them these:

1

@State doesn't persist

Every @State variable dies when the app closes. That's by design. Use a real persistence tool for data that should survive.

2

Match the tool to the data

One value → @AppStorage. List of structs → JSON file. Database with queries → SwiftData.

3

Persistence lives in the ViewModel

The View never reads or writes files directly. The ViewModel handles save/load. That's MVVM.

4

Call save() everywhere

For JSON: every function that mutates your array must call save(). Miss one and you lose data.

5

SwiftData is the future

For iOS 17+ apps, SwiftData is what Apple recommends. Learn JSON files first to understand the foundation, then graduate.

⚡

Test by killing the app

Real test of persistence: open app, do something, FORCE-QUIT (don't just close), reopen. Did your data come back?
